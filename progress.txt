YOUTUBE IDEA SCOUT — ENGINEERING MEMORY
========================================

This file is NOT a run log. Normal, expected pipeline output (queries
searched, captions unavailable, ideas REJECTed, fallback triggered,
fewer than MAX_REPORT_IDEAS produced) belongs in the console output,
report.html, and run_history.jsonl — not here.

Add an entry here only when something indicates:
  - a pipeline malfunction
  - unexpected systemic behaviour
  - an incorrect classification pattern
  - a data mismatch between stages
  - repeated parsing failures
  - relevance/territory leakage
  - a quality regression
  - a newly-discovered architectural weakness
  - a human/Scout disagreement worth watching for a repeated pattern

Before modifying a stage, read this file for previous issues concerning
that stage. Do not knowingly reintroduce a previously resolved problem.
When a new fix contradicts an earlier decision, record why the earlier
approach was superseded — don't just delete it. Do not delete historical
resolved entries; append a RESOLUTION entry that references the original.

Human / Scout disagreement convention:
When a human reviewing the report disagrees with a Scout verdict (would
have MAKEd a REJECT, or vice versa), log it here with STATUS: WATCH —
not STATUS: OPEN. A single disagreement is anecdotal and proves nothing
about the editorial gate; do NOT change Stage 6's prompt, scoring
weights, or veto rules in response to one WATCH entry. Only promote a
WATCH to an OPEN engineering issue once a repeated pattern emerges
across multiple runs/entries pointing at the same root cause. Format:

  STATUS: WATCH
  AREA: Human / Scout disagreement
  SCOUT VERDICT: ...
  HUMAN VERDICT: ...
  QUERY: ...
  REASON: ...
  NEXT ACTION: Look for repeated examples before changing editorial rules.

2026-08-21 | run_id: (pre-run_id, 2026-08-21 production run)
STATUS: RESOLVED
AREA: Stage 3 scoring — composite score ceiling
SEVERITY: HIGH

PROBLEM:
The `competition` signal was `1 - video_count/MAX_SATURATION_COUNT`, but
Stage 2 caps every search at MAX_SEARCH_RESULTS_PER_QUERY=5 results, so
video_count was ~5 for 99.6% of ideas — a near-constant contributing a
fixed +0.15 to every score. Composite score could never exceed 0.95.

EVIDENCE:
64 of 6,028 ideas in the 2026-08-21 production run scored exactly 0.95
(the ceiling). Survivor selection took the first 30 of those 64 in
enriched.json order, which traced back to Stage 2's search_results.json
key order -- itself an artefact of which of the 4 worker threads
happened to finish first. Re-running on the same data could have
returned a different 30 survivors.

FIX (v0.2, 2026-08-22):
`competition` now measures the average views/day across the WHOLE
competing field (not just the top result), normalised against
COMPETITION_FIELD_VPD_CAP. Final Stage 3 sort changed to
`(-idea_score, query)` — deterministic tiebreak, independent of thread
completion order.

VERIFICATION:
Re-scored the full 6,028-idea production dataset with the new logic:
distinct score values rose from 2,017 to 2,314; max-score ties dropped
from 64 to 1. Shuffled the input dict order and re-ran scoring -- ranking
was byte-identical to the unshuffled run.

LESSON:
A "competition" or "saturation" signal derived from a count that is
itself capped by a fixed query parameter (MAX_SEARCH_RESULTS_PER_QUERY)
will silently degenerate into a constant. Check the actual value
distribution of every signal before trusting a composite score built
from it -- a signal that never varies is worse than one that's merely
noisy, because it hides inside a plausible-looking weighted sum.

2026-08-21 | run_id: (pre-run_id, 2026-08-21 production run)
STATUS: RESOLVED
AREA: Stage 1/3/4 channel_fit — "why" domination
SEVERITY: HIGH

PROBLEM:
CHANNEL_FIT_KEYWORDS was an unweighted list including "why". Two matches
maxed channel_fit at 1.0. "why" matched 45.9% of all Stage 1 output on
its own (it's query-structure framing, not topic); paired with "humans"
(8.7%) it maxed channel_fit for any "why are humans..." query regardless
of actual subject matter. psychology/evolution/behaviour -- the terms
that actually describe the channel -- fired ZERO times in the whole
production run.

EVIDENCE:
28 of 30 report cards in the 2026-08-21 production run were "why are
humans [X]" phrasings; 5 of those were near-duplicate "apex predator"
framings of the same underlying video idea.

FIX (v0.2, 2026-08-22):
CHANNEL_FIT_KEYWORDS is now a weighted dict. "why" carries zero weight
by design -- deliberately excluded, not just down-weighted. Specific
topical terms (psychology, evolution, behaviour = 0.9-1.0) outweigh
broad ones (human/humans/body = 0.4-0.5). Logic lives once, in
common.channel_fit_score(), shared between Stage 1's pre-search gate
and Stage 3's scoring signal.

VERIFICATION:
channel_fit_score("why are humans apex predators") -> 0.417 (was 1.0).
channel_fit_score("why does psychology explain human behaviour") -> 1.0
(correctly still maxes). On the v0.2 live run, a query hitting "brain"
(weight 0.8) scored channel_fit 1.0 while plain "why are humans X"
queries scored 0.417 -- topical terms now outrank generic phrasing.

LESSON:
A keyword-count relevance signal degenerates toward whichever word is
structurally common in the seed list, not whichever word is topically
meaningful. Weighting by specificity (and explicitly zero-weighting
query-structure words) is cheap and fixes this; an unweighted OR-match
list does not scale past a handful of very carefully chosen terms.

2026-08-22 | run_id: 20260822-0825
STATUS: RESOLVED (via editorial gate, not via Stage 1 keyword changes)
AREA: Editorial relevance — franchise/pop-culture territory leakage
SEVERITY: MEDIUM
RESOLVES: the OPEN entry above (2026-08-22, franchise/pop-culture leakage)

FIX:
v0.21 added an explicit editorial veto to the Stage 6 prompt: "A
candidate MUST be REJECT if it does not belong to the intended
scout/content territory, regardless of demand, hook or makeability" --
plus a required `fit_assessment` field the model must justify. This
sits downstream of Stage 1's cheap channel_fit_score() keyword gate
(unchanged, still lets these through) and catches what the keyword gate
structurally cannot: "humans" appearing in a phrase that is actually
about franchise lore, not the channel's real subject.

VERIFICATION:
Re-ran the exact same 20 survivors (same run, same enriched.json/
survivors.json as the OPEN entry above) through the new Stage 6.
Both flagged candidates were REJECTed:
  "why are humans killing autobots in age of extinction"
    -> gap_assessment: inadequate, fit_assessment: inadequate
    -> reasoning: "franchise/film analysis, not human psychology
       explainer content"
  "why are humans in star wars"
    -> gap_assessment: inadequate, fit_assessment: inadequate
    -> reasoning: "off-territory for the query"
Full run: 20 evaluated, 14 MAKE / 6 REJECT, 0 editorial evaluation
failures. The veto also caught territory drift the OPEN entry hadn't
anticipated (e.g. "why are humans created" -> REJECT, fit=inadequate,
"fundamentally metaphysical... belongs to theology/philosophy
territory") and a genuine no-gap case despite strong fit ("why are
humans monogamous" -> REJECT, gap=inadequate, fit=adequate, existing
competitors already cover the question from every angle).

LESSON:
A cheap keyword-based gate (Stage 1's channel_fit_score) is the right
tool for pruning obviously-irrelevant queries before an expensive
network search, but it cannot distinguish topical use of a word from
incidental use ("humans" in a psychology query vs. "humans" inside
Transformers lore). That distinction needs semantic judgement -- an
LLM editorial gate downstream, evaluated per-candidate against actual
competitor content, not a wider keyword list upstream. Keep the cheap
gate cheap; do the semantic work only on the small number of survivors
that reach Stage 6.

`which <tool>` working just because it works interactively. Test cron
scripts by simulating cron's actual environment (`env -i ... bash -c`),
not by running them from an interactive shell.

2026-09-01 | run_id: 20260901-1531
STATUS: OPEN
AREA: Report display — "Competition" score has inverted semantics, misleads a human reader
SEVERITY: MEDIUM-HIGH

PROBLEM:
Lee's review flagged several report cards showing "Competition: 0.0"
alongside competitor videos with very high view counts/velocity, and
correctly identified this as "dangerous" -- a human reading "Competition:
0.0" naturally reads it as "no competition" (good), but that is
backwards. Verified in stage3_enrich.py:104-105:

    avg_field_vpd = sum(views_per_day for all returned videos) / video_count
    competition = round(max(1 - min(avg_field_vpd / COMPETITION_FIELD_VPD_CAP, 1.0), 0), 3)

This is intentionally inverted FOR SCORING PURPOSES -- it's added
positively to idea_score (line 123: `+ competition * 0.20`), so a "good"
(open) opportunity needs a HIGH competition value. A value of 0.0 means
avg_field_vpd already meets or exceeds COMPETITION_FIELD_VPD_CAP (2000)
-- i.e. maximum field saturation, the WORST case, not the best.
Confirmed against this run's own survivor data: "why does the human
body store fat" shows competition=0.0 with raw_best_vpd=361,618/day (one
competitor is doing 361K views/day); "what happens if humans eat another
human" shows competition=0.0 with raw_best_vpd=24,058/day. The formula
itself is correct and intentional for scoring; the defect is that
stage7_report.py's secondary-signals row prints this raw internal value
directly as "Competition: {value}" with no framing, so a human reading
the report has no way to know 0.0 means saturated rather than open.

EVIDENCE:
data/survivors.json, "why does the human body store fat":
signals.competition=0.0, signals.raw_best_vpd=361618.5.
data/survivors.json, "what happens if humans eat another human":
signals.competition=0.0, signals.raw_best_vpd=24058.0.
Lee's review (Waystation 447bac5c3a) independently caught 4 instances of
this same confusion by eye (cannibalism, DMT, body fat, pubic hair).

LESSON: An internal signal that's deliberately inverted relative to its
name (here: "competition" actually means "field openness," scored so
low=saturated/bad) must never be surfaced to a human reader under its
internal name and raw value without translation. This is the same class
of problem as the 2026-08-21 composition-score-ceiling issue above
(constant/misleading signal hiding inside a plausible-looking number) --
but here it's a display bug, not a scoring bug: the underlying formula
and its contribution to idea_score are working as designed, only the
report's presentation of the raw value is broken.

NEXT ACTION: Not fixed yet, per Lee's "no major changes on one sample"
instruction. When addressed, this is a Stage 7 presentation fix only
(e.g. show a LOW/MEDIUM/HIGH saturation label derived from avg_field_vpd,
or invert the displayed label to "Openness"), not a Stage 3 scoring
change -- the underlying idea_score math should not need to move.

The only "70,000" in the whole exchange is in the *same response's*
`what_competitors_miss` field -- "humans losing most body hair
70,000-120,000 years ago" -- an evolutionary-timescale fact, unrelated
to audience demand. The model appears to have reused/repurposed that
number from its own generated evolutionary narrative and restated it,
in a different field, as if it were a demand statistic. This is a
fabricated claim presented as fact, in the exact prose ("WHY MAKE
THIS?") that v0.21.1 made the most prominent part of MAKE cards.

EVIDENCE:
data/analyses/0008.json: reasoning="...a genuine gap: a 70K+ view/day
query with no video exploring..."; what_competitors_miss mentions
"70,000-120,000 years ago" in the same JSON object.
stage6_analysis.py build_analysis_prompt(): confirmed no view/demand
figure anywhere close to 70K is ever included in what's sent to Claude
for this idea.

LESSON: The Stage 6 prompt currently asks for free-text reasoning with
no constraint against inventing numbers not present in its own input.
A single hallucinated statistic in `reasoning` is easy to miss because
the surrounding prose reads fluently and the verdict (MAKE, high
confidence, gap/fit both adequate) is plausible on its own merits --
this is exactly the "confident AI sentence that can poison an otherwise
data-driven system" failure mode Lee named. Fail-closed handling
(_fail_closed()) only catches structural failures (bad JSON, missing
verdict) -- it has no mechanism for catching a well-formed but
factually ungrounded claim.

NEXT ACTION: Not fixed yet, per Lee's "no major changes on one sample"
instruction. When addressed, consider: (1) an explicit prompt
instruction to only cite numbers that appear in the competitor data
provided, never invent one; (2) a lightweight post-hoc check that flags
any numeral in `reasoning`/`what_competitors_miss` not traceable to the
prompt's own input, for human review rather than auto-correction. Watch
whether this recurs on future unchanged runs before building either.
